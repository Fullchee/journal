# Android release build speed (Expo SDK 58, RN 0.88.1)

Researched 2026-11-07 against `apps/native` on `main`: Expo `~58.0.23`, React Native 0.88.1, AGP 9.2.1, Gradle 9.4.1, Kotlin Gradle plugin 2.2.x, NDK 27.1, Apple M4 (4 performance + 6 efficiency cores, 24 GB RAM), OpenJDK 25.

Source rule: every claim links to the source that owns it. "Verified locally" means I read the installed copy under `node_modules/.pnpm` in the `wt-apk` worktree. Those files match the linked GitHub paths at the SDK 58 / RN 0.88.1 versions. **Impact** is my estimate unless the row says a source backs it.

**Measure before tuning.** Run `./gradlew assembleRelease -PreactNativeArchitectures=arm64-v8a --profile` once. Gradle writes a per-task timing report to `android/build/reports/profile/` ([Gradle CLI](https://docs.gradle.org/9.4.1/userguide/command_line_interface.html)). This shows whether C++, R8, Kotlin or JS bundling dominates, and the ranking above should be re-checked against it.

**Arm64-only saving.** React Native's docs say building one ABI "should reduce your **native build time** by a ~75% factor" ([RN build speed](https://reactnative.dev/docs/build-speed#build-only-one-abi-during-development-android-only)). That applies to native (C++) time only, not the whole 33m37s build.

**Correctness warning (not speed).** The JS bundle task can ship stale JS once builds are incremental. `createBundleReleaseJsAndAssets` only watches `*.js/jsx/ts/tsx` under the app root (`apps/native` then, the repo root since the single-package move), and it excludes `node_modules` ([`BundleHermesCTask.kt`](https://github.com/facebook/react-native/blob/v0.88.1/packages/gradle-plugin/react-native-gradle-plugin/src/main/kotlin/com/facebook/react/tasks/BundleHermesCTask.kt), root defaults to `rootProject/../` in [`ReactExtension.kt`](https://github.com/facebook/react-native/blob/v0.88.1/packages/gradle-plugin/react-native-gradle-plugin/src/main/kotlin/com/facebook/react/ReactExtension.kt); verified locally). A change only in a `.css` file (or, before the move, only in `packages/*`) leaves the task UP-TO-DATE. Force it to run each time with `./gradlew createBundleReleaseJsAndAssets --rerun assembleRelease …` ([Gradle `--rerun`](https://docs.gradle.org/9.4.1/userguide/command_line_interface.html)). It costs one Metro + Hermes run per build.

Example gradlew line combining #3, #4 and the bundle fix:

```zsh
(cd android && ./gradlew createBundleReleaseJsAndAssets --rerun assembleRelease \
  -PreactNativeArchitectures=arm64-v8a --build-cache \
  -Dorg.gradle.jvmargs="-Xmx6g -XX:MaxMetaspaceSize=1g -XX:+HeapDumpOnOutOfMemoryError -XX:+UseParallelGC -Dfile.encoding=UTF-8" \
  -Pkotlin.daemon.jvmargs=-Xmx3g \
  -Pandroid.enableMinifyInReleaseBuilds=false \
  -Pandroid.enablePngCrunchInReleaseBuilds=false \
  -x lintVitalAnalyzeRelease -x lintVitalReportRelease -x lintVitalRelease)
```

## Q3. Durable Gradle settings under CNG

Prebuild regenerates `android/`, so a direct edit to `android/gradle.properties` gets lost. Expo's own advice is to write a config plugin for that file ([CNG docs](https://docs.expo.dev/workflow/continuous-native-generation.md)). Options, best first for this project:

1. **Command-line flags in `scripts/build-apk.sh`.** Command-line flags have the highest precedence ([Gradle precedence table](https://docs.gradle.org/9.4.1/userguide/build_environment.html)). `-P` sets project properties, which the generated `app/build.gradle` reads with `findProperty('android.enableMinifyInReleaseBuilds')` etc. (verified locally). `-D` sets Gradle properties such as `org.gradle.jvmargs`; EAS does exactly this through `GRADLE_OPTS` ([EAS infrastructure](https://docs.expo.dev/build-reference/infrastructure.md#gradle-jvm-args)). Scoped to this script, nothing to install.
2. **`~/.gradle/gradle.properties`.** "user-level properties taking precedence over project-level" ([Gradle](https://docs.gradle.org/9.4.1/userguide/build_environment.html)). Prebuild never touches it, but it applies to every Gradle project on the machine. Good for `org.gradle.jvmargs`, `org.gradle.caching=true` and `kotlin.daemon.jvmargs`. The file does not exist yet on this machine.
3. **`expo-build-properties` in `app.json`.** Not installed today. Covers the documented keys: `buildArchs`, `enableMinifyInReleaseBuilds`, `enablePngCrunchInReleaseBuilds`, `usePrecompiledHeaders`, `buildReactNativeFromSource`, `buildExpoModulesCoreFromSource` ([SDK 58 reference](https://docs.expo.dev/versions/v58.0.0/sdk/build-properties.md)). `buildArchs: ["arm64-v8a"]` would make arm64-only the committed default instead of a CLI flag. Install with `bunx expo install expo-build-properties`.
4. **A local config plugin with `withGradleProperties`** for arbitrary keys like `org.gradle.caching` or `org.gradle.configuration-cache` ([mods reference](https://docs.expo.dev/config-plugins/mods.md)). The repo already has `plugins/android-shortcuts` as a pattern. Commits the setting for anyone who builds.
5. **Environment variables.** `ORG_GRADLE_PROJECT_<name>` sets a project property ([Gradle](https://docs.gradle.org/9.4.1/userguide/build_environment.html)).

## Q4. Does `expo prebuild` on every run invalidate caches?

- **Without `--clean`** (what the script does), prebuild "will layer changes on top of the existing files" ([CNG docs](https://docs.expo.dev/workflow/continuous-native-generation.md#clean)). `android/app/build` and each library's `android/build` and `android/.cxx` inside `node_modules` survive, so Gradle and ninja can stay incremental.
- **Gradle checks input content, not timestamps**, for its up-to-date checks ([Gradle incremental build](https://docs.gradle.org/9.4.1/userguide/incremental_build.html)). Rewriting a file with identical bytes should not rerun Gradle tasks. That is an inference: I did not confirm that prebuild writes byte-identical output. CMake/ninja do use timestamps, but prebuild doesn't write C++ sources.
- **With `--clean`**, `android/` is deleted, which loses `android/app/build` and the app's `.cxx`. The Gradle build cache in `~/.gradle` and ccache survive. Expo calls `--clean` "the safest way" because some config plugins aren't idempotent ([CNG docs](https://docs.expo.dev/workflow/continuous-native-generation.md#clean)).
- **When skipping is safe.** Prebuild output depends on app config, config plugins and native dependencies. `@expo/fingerprint` hashes "app dependencies, custom native code, native project files, and configuration" ([fingerprint](https://docs.expo.dev/versions/v58.0.0/sdk/fingerprint.md)). Skip prebuild when the fingerprint, computed with `android/` ignored, matches the last run. The fingerprint has an option for prebuild's `package.json` script rewrite, which `build-apk.sh` works around by hand ([same page](https://docs.expo.dev/versions/v58.0.0/sdk/fingerprint.md)). Saving is seconds.
- **The worktree is the real invalidator.** A new worktree has its own `node_modules/.pnpm/.../android/.cxx` and `android/app/build`, so every native target starts cold (verified: the `.cxx` dirs live in each worktree's `node_modules`). Only `~/.gradle` and ccache carry over.

## Q5. EAS Build

- **Hardware.** Android builders: `medium` 4 vCPU / 16 GB (default), `large` 8 vCPU / 32 GB. Each build gets a fresh VM ([EAS infrastructure](https://docs.expo.dev/build-reference/infrastructure.md)). EAS sets `-Dorg.gradle.daemon=false` ([same page](https://docs.expo.dev/build-reference/infrastructure.md#gradle-jvm-args)).
- **Caching.** An npm cache server and a Maven cache server, both on by default. ccache is saved and restored when `EAS_USE_CACHE=1` (or `EAS_RESTORE_CACHE` / `EAS_SAVE_CACHE`). A custom `cache` field in `eas.json` covers other paths ([EAS caching](https://docs.expo.dev/build-reference/caching.md)). The docs mention no Gradle build cache persistence.
- **Build times.** No primary source publishes typical Android build durations. With 4–8 vCPUs, a fresh VM and no Gradle cache, I expect EAS to be slower than a warm local build on a 10-core M4. Its value is not tying up the laptop (my inference).
- **Remote build cache provider** (`buildCacheProvider: "eas"`) only speeds up `npx expo run:android`. It is "not affected" by `eas build` ([cache builds remotely](https://docs.expo.dev/guides/cache-builds-remotely.md)). It keys on the native fingerprint, which excludes JS, so it doesn't fit a release APK with embedded JS (inference).
- **`eas build --local` doesn't help.** Local builds note "Caching is not supported" and run in a temp working directory ([local builds](https://docs.expo.dev/build-reference/local-builds.md)). Every run starts from a fresh copy: no reused `android/app/build` and no `.cxx`. It exists for debugging cloud failures.

## Q7. JDK version

- **Supported.** Gradle 9.4.1 can run on Java 25 (support since Gradle 9.1.0) and on 26 since 9.4.0 ([Gradle compatibility](https://docs.gradle.org/9.4.1/userguide/compatibility.html)). AGP 9.2's minimum and default JDK is 17 ([AGP 9.2 release notes](https://developer.android.com/build/releases/agp-9-2-0-release-notes)), and AGP needs a JDK "higher than or equal to" what its plugins require ([Android JDKs](https://developer.android.com/build/jdks)). RN 0.88.1 pins AGP 9.2.1 ([`libs.versions.toml`](https://github.com/facebook/react-native/blob/v0.88.1/packages/react-native/gradle/libs.versions.toml)). RN forces Java 17 source/target compatibility for all projects ([`JdkConfiguratorUtils.kt`](https://github.com/facebook/react-native/blob/v0.88.1/packages/gradle-plugin/react-native-gradle-plugin/src/main/kotlin/com/facebook/react/utils/JdkConfiguratorUtils.kt)), so the JDK running Gradle doesn't change the bytecode.
- **Recommended.** React Native: "we recommend JDK 17. You may encounter problems using higher JDK versions" ([RN environment setup](https://reactnative.dev/docs/set-up-your-environment?os=macos&platform=android)). Expo's local setup installs `zulu@17` ([Expo environment setup](https://docs.expo.dev/get-started/set-up-your-environment?mode=development-build&buildEnv=local&platform=android&device=physical)). AGP 9.2.0 fixed a "JdkImageTransform failure with JDK 26" ([AGP 9.2 notes](https://developer.android.com/build/releases/agp-9-2-0-release-notes)), which shows that newer JDKs do break the toolchain.
- **Speed.** No primary source claims that JDK 17, 21 or 25 changes Android build speed. Switch to 17 to match what RN and Expo test against. JDK 25 works with this Gradle, so keep it if builds succeed.
- **Daemon note.** A different JDK or Gradle version starts a separate daemon ([Android JDKs](https://developer.android.com/build/jdks)). Pin `JAVA_HOME` in the script so the daemon is reused.
